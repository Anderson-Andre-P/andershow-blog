> **GPS Simulator series · Part 4 of 6.** This is the realism that comes from map data: altitude, tunnels and bridges. Previous: [Part 3, a GPS that behaves like a real one](/blog/gps-simulator-3-a-gps-that-behaves-like-a-real-one).

The first version of the simulator published a fixed altitude and lost the signal at regular intervals, at any point of the route. They looked realistic, but they were invented numbers. An app under test could pass the test because of data no real phone would ever see.

That's why the project has a rule, which already showed up in part 1: **everything that looks real has to come from real map data. When there's no data, the app publishes nothing instead of making it up.** This post shows how that rule works for altitude and tunnels.

## Altitude and tunnels from the map

When a route is created, wherever it comes from (a routing service, an imported file or a straight line), the app sends its geometry to a **Valhalla** server:

- The `/height` endpoint returns the **terrain height** along the route, sampled every 30 meters.
- The `/trace_attributes` endpoint does _map matching_ on the route and says which stretches are **tunnels, bridges or covered areas**, based on OpenStreetMap.

With that, the behavior is:

- **Inside a tunnel the GPS loses signal**, like a real phone, and comes back at the exit.
- **On bridges, the altitude follows the deck**, not the bottom of the valley that the terrain model has underneath. The same goes for tunnels, relative to the top of the hill. On those stretches, the height is interpolated between the two ends.
- If an imported file already has the altitude of every point, the app uses the file's.
- **Without data**, for example offline or with the server down, the position is published **without altitude**, and the app says so on screen.

```kotlin
// No altitude is better than an invented one: without it the
// Location simply reports hasAltitude() == false.
val msl = (fix["altitude"] as Number?)?.toDouble()
if (msl != null) applyAltitude(location, msl, vertical)
```

The terrain profile is saved with the route, so the server is queried once per route, not on every simulation. On the route screen the summary already shows the result, with the terrain altitude and the number of tunnels on the path.

## The geoid detail

A subtle problem showed up here. The terrain model gives the height **above sea level**. A real GPS chip reports the height **above the WGS84 ellipsoid**, a mathematical surface that doesn't match sea level. In Brazil, the difference is in the tens of meters. Publishing the terrain height directly would be a plausible number, but a wrong one.

On Android 14 or newer, the system has the `AltitudeConverter`, which knows this difference. The plugin runs a "probe": it creates a position with zero altitude on the ellipsoid and asks the converter for the matching height above sea level. The value that comes back, with the sign flipped, is the difference at that point. It's computed off the main thread and cached per region, and the published altitude ends up the same as a real GPS's.

On older versions, which don't have the converter, the app publishes the height above sea level and says so on screen. It's the same rule as before: if the right calculation isn't possible, the app says it didn't do it instead of pretending.

## Respecting public servers

By default, terrain comes from the public Valhalla server run by the FOSSGIS community, which asks for at most one request per second and for apps not to hard-code its address. The client respects that limit, the address can be changed in the settings, with a button to test the server, and the required attribution is shown on screen. A team with a lot of testers can point it at their own server.

The same goes for the map. The default is Google Maps, with a standard, satellite, hybrid or terrain map, plus traffic and place icons. You can switch to OpenStreetMap, which needs no key and whose usage policy is also respected.

For Google Maps to work, I had to set up the key in the [Google Cloud Console](https://console.cloud.google.com/): create a project, enable the **Maps SDK for Android** and generate an API key for the app. Without it, the SDK draws only an empty background and logs an authorization error (`Authorization failure`). It's a simple setup, but easy to forget when running the app on a new machine, which is exactly why the key-free OpenStreetMap option is useful.

## What I learned

- **Fake realism is worse than no realism.** An invented altitude can make a test pass by mistake. Publishing "no altitude" is more honest and more useful.
- **Geographic data hides details.** Sea level and the ellipsoid look like the same thing until you compare them with a real GPS.
- **Public servers have rules.** Limiting requests, keeping what was already downloaded, allowing the server to be swapped and showing the credits is part of using a free service well.
